# Rule: scientific method

The governing discipline of this project. Every other rule file is a specialisation of this one.

---

## The five categories

Every quantity in this project belongs to exactly one category:

| Category | Definition | Example |
|---|---|---|
| **OBSERVED** | Directly contained in the source data | A lap time in the timing file |
| **RECONSTRUCTED** | Calculated deterministically from observed data | Race order from lap count and crossing time |
| **INFERRED** | Estimated statistically, with uncertainty | Traffic-associated lap-time loss |
| **ASSUMED** | Chosen because the data do not identify it | A tyre-degradation coefficient |
| **SIMULATED** | Generated by the race simulator | A Monte Carlo race outcome |

**Never silently convert one category into another.** This is the single rule that most protects the project's credibility, because the conversions are subtle and happen through wording rather than through code.

Specific prohibitions:

- An inferred traffic exposure is **not** an observed overtake.
- An assumed tyre-degradation parameter is **not** measured tyre degradation.
- The team's real pit strategy is **not** ground truth.
- A simulated race outcome is **not** a prediction of what would have happened.
- A reconstructed race position is **not** an official classification unless validated against one.

## How conversions actually happen

Rarely through a deliberate claim. Usually through:

- **A variable name.** `overtakes` instead of `candidate_exposures` will, three months later, be described as overtakes in a report.
- **A plot title.** "Time lost to traffic" asserts causation; "Lap residual under inferred exposure" describes what was plotted.
- **A dropped qualifier.** "Estimated pit loss" becomes "pit loss" in the summary, then "measured pit loss" in the bullet.
- **A default value.** An ASSUMED parameter with a plausible default gets treated as known because it never had to be discussed.

Guard at the point of naming. If the variable name would mislead someone reading only the code, rename it.

## Measurements before models

Before choosing any estimator, establish:

- what the source measures;
- what the source does not measure;
- what can be derived exactly;
- what must be inferred;
- what cannot be identified at all.

Do not start by choosing a model class. XGBoost, neural networks and reinforcement learning are answers to questions that have not been asked yet.

---

## Baselines before complexity

Every sophisticated model requires a simpler comparator, fitted first:

| Target | Baseline before the sophisticated version |
|---|---|
| Traffic effect | Raw matched-group difference, before mixed-effects regression |
| Pace | Median or simple hierarchical baseline, before boosted trees |
| Strategy | Fixed-stint deterministic simulation, before the optimiser |
| Search | Exhaustive grid, before Bayesian optimisation or RL |
| Retrieval | Simple keyword or embedding retrieval with citations, before an agent framework |

If the complex model does not beat the baseline by more than the uncertainty on the comparison, the baseline wins. Report that.

---

## Null results

**A result that fails to support the hypothesis is a result.** It gets logged in `EXPERIMENT_LOG.md` with the same care as a positive one.

Do not adjust exclusions, feature definitions, thresholds or model choice in order to make an effect appear. If the traffic effect is weakly identifiable from timing data, the correct output is a clearly bounded finding, such as:

> Sector timing data provide evidence for an association between inferred multi-class traffic exposure and positive lap-time residuals, but the available data cannot uniquely identify individual overtakes or establish a causal per-overtake time loss.

That is scientifically stronger, and more impressive in an interview, than a fabricated effect size.

---

## Never invent evidence

- No fabricated metrics, counts, p-values, effect sizes or performance numbers.
- No citation of a paper, regulation or dataset that has not been retrieved and read.
- No filling of an unknown field with a plausible value. Write `UNKNOWN — requires validation`.
- No presentation of a planning estimate as a measurement. The data-volume figures in `Strategy.md` §8 are estimates and are labelled as such until measured counts replace them.

If a number is needed and not available, say so and stop. An honest gap is recoverable; an invented number discovered later is not.

---

## Association is not causation

Traffic is the most vulnerable quantity in this project. A lap may be slow because the car encountered a slower-class car — or because of a driver error, tyre degradation, fuel load, a mechanical issue, a yellow flag, changing weather, deliberate tyre or fuel saving, or because it was an in-lap or out-lap.

Control for observable confounders and state plainly which remain uncontrolled. The remaining confounders belong in the same paragraph as the result, not in a limitations section at the end that nobody reads.

---

## State limitations where the result is stated

Whenever a modelling choice affects scientific interpretation, the limitation appears **alongside the result** — same section, same figure caption, same summary sentence. Not in an appendix.

The test: if someone quoted the result sentence alone, would it mislead? If yes, the qualifier belongs inside that sentence.

---

## The three standing questions

Every session, and every result, should be able to answer:

1. **What do we actually know from the data?**
2. **What are we inferring from the data?**
3. **What are we assuming because the data do not contain the required information?**

Keep the categories separate and the project stays credible.
