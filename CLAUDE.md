## 1. Project identity

An end-to-end data and decision system for **multi-class endurance-racing pit strategy**, built on real FIA WEC timing data.

The vertical slice is:

```
WEC timing data → ETL/QA → statistical models (pace, traffic)
→ stochastic simulator → optimiser → explainable output (RAG + tool-calling LLM)
```

The numerical recommendation is produced by the simulator and optimiser. The LLM explains and cites; it never computes the answer.

The purpose is a technically credible portfolio project for graduate Data Science / Data Engineering / ML-AI Engineering roles. **Depth and validation beat technology count.**

## 4. Scientific principles

Every quantity in this project belongs to exactly one category, and the category must be stated wherever it matters:

| Category | Meaning |
|---|---|
| **OBSERVED** | Directly contained in the source data |
| **RECONSTRUCTED** | Calculated deterministically from observed data |
| **INFERRED** | Estimated statistically, with uncertainty |
| **ASSUMED** | Chosen because the data do not identify it |
| **SIMULATED** | Generated by the race simulator |

**Never silently promote one category into another.** In particular:

- inferred traffic exposure is not an observed overtake;
- an assumed tyre-degradation parameter is not measured degradation;
- the team's real pit strategy is not ground truth;
- lap count is not independent sample size (laps are clustered within cars, drivers, stints, races and circuits).

Other standing rules:

- **Measurements before models.** Establish what the source does and does not measure before choosing an estimator.
- **Baselines before complexity.** Every sophisticated model needs a simpler comparator.
- **A null result is a result.** Do not adjust exclusions, feature definitions or model choice to make an effect appear.
- **Never invent evidence.** No fabricated metrics, counts, p-values, citations or performance numbers. If a number is not yet measured, write `UNKNOWN — requires validation`.
- Whenever a modelling choice affects scientific interpretation, make the limitation explicit in the same place the result is stated.

Detailed rules: `.claude/rules/scientific-method.md`, `statistics.md`, `simulation.md`, `rag.md`.

## 5. Data provenance

- **Raw WEC / Al Kamel timing data must never be committed.** Al Kamel asserts ownership of the timing data; redistribution is not permitted without permission. `.gitignore` enforces this — do not weaken it.
- Every ingested file records: source URL, event, session, download timestamp, filename, size, SHA-256, and whether it is race-wide or partial.
- `data/raw/` is faithful source material — never edit in place. `data/interim/` is standardised and validated. `data/processed/` is analytical marts.
- Invalid rows are **flagged, not deleted**. Retain the reason for exclusion.
- Transformations are deterministic and re-runnable from `data/raw/` with one documented command.
- Only tiny synthetic fixtures (`tests/fixtures/`) are committed. Synthetic fixtures must be clearly labelled as synthetic.
- The README explains how a third party obtains the source data themselves.

Details: `.claude/rules/data-engineering.md`.

## 7. Testing expectations

- Any deterministic transformation gets a unit test before it becomes an input to a model.
- Race-state reconstruction, gap calculation and stint detection require deterministic tests on synthetic fixtures **before** they feed the traffic model.
- The simulator requires invariant / property tests (race time never decreases, tyre age cannot fall without a pit event, traffic disabled ⇒ zero traffic loss, and so on).
- Data-quality checks are tests, not one-off notebook cells.
- Tests and CI must run without access to the proprietary raw dataset.
- Reproducibility is a test target: seeded runs produce identical output.

Details: `.claude/rules/testing.md`.

---

## 8. Validation discipline

- Generalisation claims use **race-level** (and where possible circuit-level or temporal) holdout. Never randomly split lap rows from the same race between train and test for a headline result.
- Separate model fitting, parameter tuning, validation and final demonstration races. Do not tune and report on the same races.
- No leakage: a feature used for a decision at race time may only use information available at that moment.
- Report uncertainty (bootstrap intervals, empirical distributions, quantiles), not point estimates alone.
- Sensitivity analysis is part of a result, not an appendix.

## 10. Failure modes to actively prevent

Flag these if the project starts drifting:

- building a generic chatbot instead of a racing decision system;
- reaching for RL, deep learning or a vector database before the simulator and data are validated;
- claiming exact overtake detection without positional data;
- claiming separated fuel and tyre effects when they are not identifiable;
- adding Docker / cloud / orchestration before the local pipeline works;
- optimising for impressive terminology over defensible results.
